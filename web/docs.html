The EVM core is deliberately small: it holds the basket, accepts prices from its authorised relayer, computes the index, and accounts fees. Everything that does not need to be atomic with that lives in a separate contract. Every privileged action is owner-gated, and the owner can be migrated to a timelock (§6) so changes are proposed, delayed, then executed.

3. The oracle flow

Planet does not depend on a third-party oracle network. On the EVM deployment the core accepts a price from a single authorised relayer address and recomputes the index on-chain, which means "connecting a real data source" reduces to funding one key.

  1. The relayer builds a payload {index, price, volatility, liquidity, riskState, timestamp}.
  2. On EVM: no signature is involved at all. The relayer calls updatePrice(index, price, volatility, liquidity, riskState, timestamp) directly; authorisation is msg.sender == core.relayer.
  3. The strictly increasing timestamp is the replay guard: every call sets lastOracleUpdate, so a repeated timestamp reverts BadTimestamp. Anyone may call it, but only the relayer's call is accepted.
  4. The core checks: caller is the relayer, timestamp is strictly increasing, index in range, basket weights sum to 100%, and the price-jump guard.
  5. It recomputes the index over the active basket and stores the new value.

The push runs hourly from GitHub Actions (.github/workflows/evm-push.yml). That cadence is not cosmetic: MAX_ORACLE_AGE is 6 hours and mint() reverts StaleOracle past it (measured from oldestActiveUpdate()), so minting would be closed most of the day on a daily schedule. redeem() deliberately has no freshness guard: an exit is not blocked by a stale feed.

Which channels, and what happens when they disagree

Four independent venues are read per asset where they cover it: Yahoo (primary), Sina, Tencent and Eastmoney. Today that is 34 channel reads across 14 assets — 12 assets have two or more channels, five have four. Tencent is what makes the four ETFs (lumber/lithium/water/carbon) checkable at all, since Sina does not quote them.

The rule is not "median of everything". The primary sets the price; another channel only counts as a confirmation if it lands within 0.5%. With no confirmation the reading is published as riskState=1 (caution) at the primary's price. Averaging a dissenter is how natgas once ended up at 3.276 when the front month was 3.05: a 1% gap between venues is usually two contract expiries, not a disagreement about the same instrument. Natgas is now single-source for that reason, and soybean's Tencent quote (1% off) is rejected rather than blended — both show up as caution.

This is inspectable, not just described: /api/v1/sources lists every channel that answered, its raw reading, the confirmation count and any rejected channel with how far off it was.

The live write path is one relayer address set by setRelayer(address) (owner action). The M-of-N verifier is deployed and wired in (updatePriceSigned), and its signer set is configured with setSigners(address[], uint8) on the oracle. Today it is 1-of-1 with the same operator key; raising it to 2-of-3 is a setSigners() call — no redeploy.

4. Token, mint & redeem

On EVM, PLT is a plain ERC-20 (PlanetToken). The core is its only minter (token.minter == core), and the core keeps the supply accounting.

  • Mint: mint(uint64 deposit) pulls deposit of the collateral token (Circle test USDC, 6 decimals) from the caller with transferFrom, computes deposit·(1−fee)/index and mints PLT. It reverts NoToken when no PLT token is wired and NoDepositToken when no collateral is wired, so the core cannot mint against a number it never received, nor take a deposit it cannot tokenise.
  • Burn/redeem: redeem(uint64 burnAmount) burns the caller's PLT, pays back burnAmount·index·(1−fee) of the collateral, and decrements totalReserve by exactly that payout — the fee stays in the reserve. Both calls are on /app, which previews the contract's own arithmetic.

Fees are band-based (0.5% near the index, 1% at 3–5% off, 2% beyond, plus a below-peg redemption penalty) and split 30% burn / 40% reserve / 20% staking / 10% risk fund.

5. The fund — design, not deployed

PlanetFund is the "real product" shape: subscribers deposit, a custodian set confirms the purchase at the attested NAV (M-of-N, and shares are minted only on that confirmation — never on a deposit alone), and redemption is two-phase. Redemption is trustless about the shares: the subscriber transfers shares to the fund's own balance, the receipt must come from that balance, the shares are burned, and only then can the custodian confirm the payout. Shares that never left the subscriber cannot be paid out. Status: design; there is no Fund contract in the Arbitrum deployment.

6. Governance — timelock live; PLTG is design

  • PLTG / PlanetGov — design. There is no governance token or staking contract in the Arbitrum deployment; the reward-per-share and voting mechanics are documented but not live.
  • Basket changes are owner actions on the core: append a commodity, re-weight one (15% cap), or retire one by setting its weight to 0. Base prices can never be changed.
  • Delay: on testnet the core owner is a 60-second PlanetTimelock, so every privileged call is propose → wait → execute. Production intends a multisig as the timelock's owner and a longer delay.

7. Public API

GET /api/v1/statusLive index + full basket + accounting as JSON. Versioned path, ETag + 304, one error envelope, 503+Retry-After when the RPC is rate-limited.
GET /api/v1/oracleIs the price feed alive and sane? The age of the last push against the 6-hour limit, the relayer address (single key, no threshold), whether base prices are locked, and — with ?full=1 — the weights check plus frozen/caution commodities and the signer keys. Cheap by default so a monitor can poll it. 503 means "could not read the chain", never a false "healthy".
GET /api/v1/sourcesEvery price channel, its reading, and whether it confirmed the primary — the raw material behind each pushed price.
GET /openapi.jsonThe OpenAPI 3.1 contract — generate a client from it instead of hand-parsing.
/api/statusDeprecated alias; replies 308 with Deprecation / Sunset / Link headers.

The API is read-only by design. There is no endpoint that signs or submits a transaction for you: minting and redeeming happen on-chain, signed by the user's own wallet. A custodial write API would be a funds-risk liability, so it does not exist.

9. Verification checklist

  1. Call currentPpi(), assetCount(), assets(i), baseLocked(), oldestActiveUpdate() on PlanetCore.
  2. Check weightSum() == 1000000 and no weight exceeds 150000 (MAX_ASSET_WEIGHT).
  3. Recompute the index from assets(i) with the formula in methodology §5 and compare to currentPpi().
  4. Compare oldestActiveUpdate() against the wall clock — it should be minutes, never days, old; that is the timestamp minting gates on.
  5. Confirm owner() is the timelock, not a plain wallet.
  6. Fetch /api/v1/status and confirm the numbers match your own contract reads.

10. Security & disclosure

  • Non-custodial. Planet never holds keys or seed phrases; the app asks the user's own wallet to sign. Any message asking for a seed phrase is not us.
  • Unaudited. No third-party audit has been completed; that is the gate before any mainnet deployment. Treat the code as research software.
  • Known failure modes are tested: fee-bucket netting (30/40/20/10), token-required mint/redeem, collateral pulled before state changes, signed-payload domain separation, non-positive amount rejection, and a staleness guard on minting.
  • Disclosure: see /.well-known/security.txt.
