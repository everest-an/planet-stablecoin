Planet — an on-chain commodity purchasing-power index.

Planet (PLT) aggregates the real prices of a basket of global commodities into a single on-chain purchasing-power index (PPI), expressed as a ERC-20 token on Arbitrum Sepolia. This page is the complete whitepaper — mathematics, basket, stability, oracle, governance, tokenomics, worked simulation and technical appendix.

Which implementation this document describes. 1. Overview

Planet (PLT) aggregates the real prices of a basket of global commodities — energy, metals and agriculture — into an on-chain purchasing-power index (PPI), and expresses that index as an ERC-20 token on Arbitrum Sepolia. A wallet can mint PLT by depositing test USDC at the current PPI, and redeem PLT for test USDC from the reserve.

Phase 1 status. Planet is a proof-of-concept synthetic index token. It holds no real commodity reserve and is not a fully-collateralised stablecoin. The full “1:1 commodity reserve” variant is a future phase that requires an RWA custodian and regulatory compliance.

3. The index (PPI)

The owner configures a weighted basket — currently 14 commodities — and locks the base prices on-chain. A relayer submits signed per-asset prices; PlanetCore recomputes the PPI from the live basket. An asset flagged as frozen is excluded and the remaining weights are re-normalised; if nothing is active the index is undefined and minting is refused.

4. Mint / burn and fees

Minting pulls test USDC and issues PLT at the current PPI, net of a tiered fee. Each fee is routed 30% burn · 50% reserve · 20% staking, with a 10% risk-fund carve-out taken from the reserve bucket (net 30 / 40 / 20 / 10). Redeeming burns PLT and pays test USDC from the reserve in the same transaction.

5. Stability mechanisms

  • Band circuit-breaker: minting is refused when the index is undefined, and blocked beyond a 15% deviation.
  • Fee slope: fees rise above a 5% deviation; redemption is asymmetric and capped.
  • Arbitrage incentive: a fee rebate when the index is rich, to pull it back.
  • Stabilisation bonds & risk fund: absorb selling pressure below peg; part of each fee funds a risk reserve.

6. Oracle

Prices are sourced off-chain from up to four independent channels per asset: Yahoo Finance is the primary and Sina / Tencent / Eastmoney are confirmations within 0.5% (not a median). PlanetCore applies guards: strictly increasing timestamps, a single-update price-jump limit, a 6-hour freshness ceiling on minting over the stalest active asset, and a caution state when a reading has no confirmation. The live write path is an authorised relayer; the SignedPriceOracle adds an ECDSA M-of-N path, deployed today with a 1-of-1 signer set.

7. Governance

All privileged actions require the owner. Ownership is migrated to a timelock and routed through Propose → delay → Execute, giving holders a reaction window; the timelock’s owner should be a multisig. The PLTG staking/voting design is documented but not deployed in this Arbitrum deployment; parameter authority is the timelock. The original DAO plan, and exactly what is live today, are set out in §9 of the complete edition.

8. Status & roadmap

  • Now: Arbitrum Sepolia — PlanetCore + PLT (ERC-20) + Timelock + SignedPriceOracle; 14-asset basket; hourly price push; 70 Foundry tests. The site, the public API and /app (mint/redeem against test USDC) run against this deployment. The live oracle is a single relayer key; the M-of-N verifier is deployed but its signer set is 1-of-1.
  • Next: third-party audit; multisig owner; raise the signer set to 2-of-3; production oracle sources.
  • Later: 1:1 commodity reserve via an RWA custodian, proof-of-reserve and compliance; PLTG governance.

9. Disclaimer

This is a technical proposal and a proof-of-concept, not investment advice. It is not audited. Commodity prices are volatile and an early-stage index token may diverge materially from its theoretical PPI. Do not use with value you cannot afford to lose.

1. Problem & design goals

  • Single commodities (gold, oil) are volatile and concentrated; multi-commodity exposure is hard to hold on-chain.
  • Inflation hedging exists, but there is no public, verifiable object equal to “one token = a basket of global commodity purchasing power”.
  • Design goals: (i) a transparent index whose formula runs on-chain; (ii) a token redeemable through the commodity layer; (iii) failure isolation, so one bad feed cannot poison the whole index; (iv) no custodian in Phase 1; (v) every privileged change observable and delayed; (vi) no self-built exchange.

2.3 Data, fixed point and the EVM

The EVM has no floating point. All arithmetic is integer fixed-point: the index uses a 1e6 scale (1e6 ≡ 1.0), the weight sum is 1e6, and reward accounting uses 1e12. State lives in ordinary contract storage: a fixed Asset[] array plus scalar accounting fields. Solidity 0.8 checked arithmetic reverts on overflow, and mixed uint64/uint256 expressions are explicitly cast. PLT is an ERC-20; Core.totalSupply is the accounting source, and the token supply matches because mint/burn are Core-only.

2.5 Asset isolation — how one bad input is stopped from becoming a protocol failure

Isolation is not a single switch. It is enforced at four layers, each with a test that fails if the layer is removed:

LayerMechanismWhat it prevents
Price inputevery asset carries its own lastUpdate; a second channel confirms only within 0.5% (§7.1)one fresh input standing in for thirteen stale ones
IndexriskState = FROZEN assets are skipped and the remaining weights renormalised (eq. 15)a broken commodity silently distorting the index
Mintingthe staleness gate reads the oldest active asset, and the owner can freeze a dead feed to reopen itminting against week-old data; or a dead feed blocking minting forever
Accountingcollateral, fee buckets and risk fund are labels on one balancenothing — see the limit below

The honest limit. This is data and index isolation, not custody segregation. The collateral, the fee buckets and the risk fund sit in the same contract balance — the buckets are accounting labels. PLT is only as good as the operator honouring redemptions, and separating customer collateral from protocol funds needs a custodian and a legal wrapper that this build does not have. Anyone reading §2.5 as “your money is ring-fenced” has read one word too many.

3.2 Definition

Let assets be i = 1…n with weight wi, locked base price Pibase and current price Pi. Let A be the set of active (non-frozen) assets.

(1)PPI = Σi∈A wi · PiPibaseΣi∈A wi (2)PPI = 0  if  Σi∈A wi = 0  (no active asset ⇒ the index is undefined)
  • Constraint: Σi wi = 106 and 0 ≤ wi ≤ 150000.
  • Re-normalisation — dividing by the active weight sum — is what makes a frozen asset disappear cleanly instead of silently biasing the index.
  • Equation (2) is a safety property: an early implementation returned 1.0 when everything was frozen, which allowed minting against a fabricated index. It now returns 0 and minting is refused (§4.1).
  • Target price: PricePLT = PPI × USDbase, with USDbase = $1.00 at genesis — PLT tracks the ratio of the basket’s price to the locked base, not a fixed dollar.

3.3 Worked example

Take three assets A, B, C with weights 0.5 / 0.3 / 0.2 (encoded 500000 / 300000 / 200000), base prices 100 / 50 / 80, current prices 110 / 47.5 / 84:

(1a)A ×1.10   B ×0.95   C ×1.05 (1b)PPI = 0.5(1.10) + 0.3(0.95) + 0.2(1.05) = 0.550 + 0.285 + 0.210 = 1.045 (1c)if B freezes: PPI = (0.5·1.10 + 0.2·1.05) / (0.5 + 0.2) = 0.76 / 0.70 = 1.0857… (1d)if A, B and C all freeze: PPI = 0 ⇒ minting refused (eq. 2)

(1c) is the consequence readers should internalise: excluding a falling asset raises the index. That is arithmetically correct — the remaining basket really is worth more per active unit — and is exactly why the freeze state is a governed, observable action rather than an automatic one.

4. Mint, redeem & fees

Let D be the value deposited, B the PLT burned, and f the fee rate for the current band.

(3)M = D · (1 − f) / PPI   PLT minted (4)R = B · PPI · (1 − fburn)   value returned (5)F = D · f   fee collected

4.1 Mint gating

(6)tnow − oldestActiveUpdate ≤ MAX_ORACLE_AGE = 6 h   freshness of the stalest active asset (7)PPI > 0   the index is defined (eq. 2)

(6) uses the stalest active asset, not the most recent push: one fresh input must not make thirteen stale ones look current. (7) closes the frozen-basket hole. These are the only two “market” reasons a mint can be refused.

4.2 Fee routing

(8)F = Fburn + Freserve + Fstake + Frisk burn 30% · reserve 50% · staking 20%, then 10% of the fee is carved into the risk fund (net 30 / 40 / 20 / 10)

Why the reserve bucket is the largest: in the fully-backed future phase the reserve must grow at least as fast as the index, otherwise the collateral ratio decays. The v1 whitepaper used 45 / 30 / 25 (burn / reserve / staking); this is a deliberate re-weighting, not an oversight (§10.2).

4.3 The redemption path

Redemption is a single synchronous call: redeem(burnAmount) burns PLT, computes the payout from the index and the burn fee, decrements totalReserve, and transfers test USDC back to the caller. There is no mirror: the token and the core accounting move in the same transaction, so they cannot drift.

Redemption is deliberately not symmetric with minting: exiting below peg carries an extra penalty (bounded by (10)), while minting below peg is what re-floats the index. When the index is rich the protocol pays a rebate so an external arbitrageur is rewarded for pushing price back toward PPI.

Below peg, holders can subscribe at a discount to be repaid a premium. Bonds are requested by the holder and settled by the operator — asking to redeem can never destroy a claim before it has been paid. Owner-opened, owner-priced, bounded. 5.6 Hard limits

A global pause (setPaused) and the >15% mint refusal are hard circuit-breakers that do not depend on incentives. (A per-transaction cap is part of the design; the EVM core does not implement one yet.)

6. CAM adapter layer — failure isolation

The CAM layer is a design in this deployment. The EVM core carries the standardised fields (price, volatility, liquidity, riskState) with riskState ∈ {normal, caution, frozen}, and the relayer writes them with each price; there is no separate CAM adapter contract yet.

(15)frozen ⇒ i ∉ A  ⇒ excluded from (1) and exempt from rebalancing

This is the core safety property: a single bad source, price or liquidity event is contained. The protocol propagates the state — raising fees, lowering limits, freezing one asset — rather than the error, so one commodity cannot poison the index. Adding or retiring a commodity does not require touching the core.

7. Oracle & price integrity

7.1 Sources

The relayer reads up to four independent channels per asset. Yahoo Finance is the primary because it covers all 14 instruments under the same instrument definition; Sina, Tencent and Eastmoney are confirmations only when they land within 0.5%. The rule is primary + confirmation count, not a median: a 1% gap between venues is usually two different contract expiries, and averaging those blends two different assets. Natural gas is deliberately single-source because the other venues quote a later expiry. The full matrix is published at /api/v1/sources.

7.2 Verification

(16)accept ⇔ onlyRelayer(updatePrice)  ∨  |{ s ∈ S : verify(H, σs, pubs) }| ≥ threshold H = ECDSA digest bound to the oracle address + chain id; distinct signers enforced by a used-signer bitmap; EIP-2 malleability rejected

The live write path is the authorised relayer. The SignedPriceOracle is deployed and wired for updatePriceSigned, but its signer set is 1-of-1 today; raising it to 2-of-3 is a setSigners([a,b,c], 2) call, not a redeploy.

7.3 Guards

(17)tpayload > tlastUpdate  strictly increasing ⇒ replay is dead (18)|Pnew − Pold| / Pold ≤ 50%  single-update jump limit; owner forcePrice is the timelocked escape hatch (19)no confirmation within 0.5% ⇒ riskState = caution  divergence guard

7.4 Freshness model

ClockValueMeaning
On-chain mint guard6 hminting is refused when oldestActiveUpdate is older than 6 h — a safety property (eq. 6)
API health6 h/api/v1/oracle reports fresh=false past the same limit and lists any stale inputs

The hourly push leaves roughly five hours of slack. Redemption deliberately has no freshness guard: an exit should not be blocked by a stale feed, and the payout is bounded by the reserve and the fee cap.

7.5 Key management

The live writer is Core.relayer, a dedicated hot EOA; the owner / timelock key is separate. The SignedPriceOracle keeps its own signer set and threshold. Rotating any of them is an owner action through the timelock, never a direct EOA call. A leak of the relayer key can submit guarded prices, but cannot move funds or change ownership.

8. Rebalancing (RTRA)

(20)ΔAi = ( wi − Vi / Σj Vj ) · T
  • ΔAi — value to trade in asset i; wi — target weight; Vi — current holding; T — total reserve.
  • Trigger: drift-based and risk-adaptive — a frozen asset is not traded, and high volatility / low liquidity raises the trigger threshold.
  • Execution is deliberately out of scope: Planet does not build a DEX/AMM/order-book. On Arbitrum, trades would be routed to external venues (e.g. Uniswap, Camelot); the protocol only computes the target.
  • Status: RTRA is a design in this deployment; the EVM core does not implement rebalancing yet.

9. Governance & the DAO plan

9.1 What the original whitepaper (v1.0) planned

The first whitepaper specified a governance token PLTG, fixed at 1,000,000,000 units, with a published allocation and vesting schedule:

The DAO was to control, by PLTG vote:

  • commodity weights wi — “adjusted quarterly by DAO vote”;
  • fee rates (stated range 0.3%–0.8%);
  • the PPI deviation thresholds (±3% default);
  • the choice of reserve custodian.

PLTG captured value two ways: staking dividends — a share of fees paid periodically in stable value — and voting power. Liquidity providers of the PLT/stable pool were to receive PLTG rewards. The roadmap scheduled DAO governance launch in Q2 2026. Anti-fragility commitments included spreading reserve assets across 10+ venues and a minimum collateral ratio of 105%.

The v1 fee split was 45 / 30 / 25 (buyback-burn / reserve / staking); the implemented split is 30 / 50 (+10 risk) / 20 — the reserve bucket was deliberately re-weighted upward.

9.3 Privileged actions and the timelock

(21)Execute ⇔ now ≥ eta = proposeTime + delay  ∧  ∃ pending (dest, body)

Owner-gated operations: basket assets and weights (setAsset), the token / deposit-token / oracle / relayer setters, pause, forcePrice, setRiskState, and ownership itself. Once the owner is the timelock, a direct EOA call to these functions is rejected; changes must go through propose → delay → execute. The delay is the holders’ reaction window, and the timelock’s owner should be a multisig.

11. Fund (tokenised ETF shares) — design

The Fund is the L4 wrapper: it issues shares against a basket of ETF positions at NAV, so holders get fund-style exposure rather than a purely synthetic index. Actions that move NAV (mint, custody changes) are custodian-signed under an M-of-N policy; redemption is trustless — the fund receives its own ERC-20 shares on a normal transfer and burns them, releasing the claim, without an operator having to co-operate. Status: design; there is no Fund contract in the Arbitrum deployment.

12. Trust & threat model

ActorCanCannot
Usermint / redeem / transfer — always signing in their own wallet—
Relayer hot keysubmit price updates, bounded by eq. 16–19touch ownership, parameters or funds
Ownerchange parameters after the timelock delayact instantly; bypass propose → delay → execute
Custodian (future)attest NAV under an M-of-N policymove user assets unilaterally
  • Owner-key compromise is the dominant risk; the delay is the only mitigation — hence multisig + a longer delay before mainnet.
  • Hot-key compromise is bounded: prices only, inside the jump band and divergence freeze; funds are unreachable.
  • Payload replay is defeated by the strictly increasing timestamp (eq. 17) and the oracle's domain separation (oracle address + chain id).
  • By design, not fixed: redemption has no freshness guard (asymmetric with minting; an exit is not blocked by a stale feed), the fee buckets are accounting labels rather than separate balances, and PLTG / executed proposals are design. These are documented, not hidden.

15. Risks & compliance

  • Index divergence — the reserve is test USDC, not the commodity basket; market price may diverge materially from PPI.
  • Oracle — source coverage and availability; the guards bound but do not eliminate this.
  • Liquidity — thin at cold start, so the market price is manipulable.
  • Compliance — enabling real mint/redeem constitutes a financial product and needs licensing/custody; Phase 1 deliberately avoids it.
  • Mechanism limits — the stability toolkit is soft (fees, bonds, incentives); it is not a substitute for real reserves.

Abbreviated excerpts from the contracts that actually run on Arbitrum Sepolia. The full source is in monad/src/.

C.1 The index (§3)

function computePpi() public view returns (uint64) {
    uint256 num; uint256 den;
    for (uint256 i; i < assets.length; ++i) {
        Asset storage a = assets[i];
        if (a.riskState == RISK_FROZEN) continue;                 // eq. (15)
        num += uint256(a.weight) * uint256(a.currentPrice) * SCALE / uint256(a.basePrice);
        den += uint256(a.weight);
    }
    if (den == 0) return 0;                                       // eq. (2): undefined, not 1.0
    return uint64(num / den);
}

C.2 Fee band (§5.1)

function feeBpsForPpi(uint64 ppi) public pure returns (uint64) {
    uint256 d = ppi > SCALE ? ppi - SCALE : SCALE - ppi;
    if (d * BPS_DENOM > SCALE * BAND_REJECT_BPS) revert BandReject();       // >15%
    if (d * BPS_DENOM <= SCALE * 300) return FEE_BASE_BPS;                  // 0.5%
    if (d * BPS_DENOM <= SCALE * 500) return FEE_MID_BPS;                   // 1%
    uint256 extraBps = (d * BPS_DENOM / SCALE) - 500;
    return uint64(FEE_HIGH_BPS + extraBps * SLOPE_BPS / 100);               // eq. (9)
}

C.3 Mint: freshness, collateral, supply (§4.1)

function mint(uint64 deposit) external returns (uint64 minted) {
    if (paused) revert IsPaused();
    if (deposit == 0) revert ZeroAmount();
    uint64 ppi = currentPpi;
    if (ppi == 0) revert NoActiveAsset();                                 // eq. (2)/(7)
    uint64 oldest = oldestActiveUpdate();
    if (oldest == 0 || block.timestamp > oldest + MAX_ORACLE_AGE) revert StaleOracle(); // eq. (6)
    // ... fee + minted ...
    if (address(token) == address(0)) revert NoToken();
    if (address(depositToken) == address(0)) revert NoDepositToken();
    if (!depositToken.transferFrom(msg.sender, address(this), deposit)) revert TransferFailed();
    totalSupply += minted;
    token.mint(msg.sender, minted);
    totalReserve += deposit;
    _routeFees(fee);
}

C.4 Redeem: burn, payout, reserve (§4.3)

function redeem(uint64 burnAmount) external returns (uint64 payout) {
    if (paused) revert IsPaused();
    if (burnAmount == 0) revert ZeroAmount();
    if (currentPpi == 0) revert NoActiveAsset();
    if (address(token) == address(0)) revert NoToken();
    // ... gross, capped burn fee, payout ...
    if (totalSupply < burnAmount) revert Underflow();
    totalSupply -= burnAmount;
    token.burn(msg.sender, burnAmount);
    if (totalReserve < payout) revert Underflow();
    totalReserve -= payout;
    if (!depositToken.transfer(msg.sender, payout)) revert TransferFailed();
    _routeFees(fee);
}

C.5 Oracle verification (§7.2)

function verify(PricePayload calldata p, bytes calldata sigs) external view returns (bool) {
    bytes32 d = digest(p);                       // domain + address(this) + chainid + payload
    uint256 usedMask; uint256 matched;
    for (uint256 k; k < sigs.length / 65; ++k) {
        (address who, bool ok) = _recover(d, sigs, k * 65);   // EIP-2 s-range check
        if (!ok) continue;
        uint256 slot = _signerSlot(who);
        if (slot == type(uint256).max) continue;              // not a signer
        if ((usedMask >> slot) & 1 == 1) continue;            // one key, one vote
        usedMask |= (uint256(1) << slot);
        if (++matched >= threshold) return true;              // eq. (16)
    }
    return false;
}

Appendix D — security & audit appendix

D.1 EVM-specific properties

  • No floating point ⇒ all invariant checks are exact integer comparisons; the classic float-rounding attack surface does not exist.
  • Reentrancy discipline: the only external calls are to the owner-wired PLT and deposit tokens. mint validates first and pulls collateral before any state change; redeem updates supply and reserve before transferring out. A non-standard deposit token remains a trust assumption.
  • Checked arithmetic: Solidity 0.8 reverts on overflow/underflow, and subtractions (supply, reserve, bond face) are explicitly guarded. Mixed uint64 / uint256 expressions are cast at every boundary.
  • Transfer results: transferFrom / transfer return values are checked; a false return reverts the transaction.
  • Timelock: ownership changes and privileged calls go through propose → delay → execute; failed inner calls are recorded (TL-2) and the delay can never be reset to zero (TL-3).

D.2 The review register

A first-party review of the earlier implementation found and fixed 10 issues, each ported with a regression test: an undefined index returned 1.0 and permitted minting; timelock ownership could bypass the delay; a failed executed action could fail silently; a voter could unstake immediately; proposal spam; bond redemption could destroy a claim without payment; the bond premium was unbounded; and a supply underflow. The EVM port added its own fixes: the fee buckets now net 30/40/20/10; mint and redeem refuse to run without a wired token; setAsset bounds-checks before indexing; and the weight sum is enforced on price updates rather than on every basket edit. The remaining design items are documented (redemption has no freshness guard; fee buckets are labels; PLTG and executed proposals are design).

D.3 What an auditor should attack

  1. Manipulating the freeze state to profit from re-normalisation (eq. 1c).
  2. Fee accounting: do the four buckets reconcile with the fee charged, and does totalReserve reconcile with the USDC balance?
  3. Payload encoding / domain separation: any ambiguity or cross-chain replay?
  4. Timelock: can dest/body be swapped between propose and execute?
  5. Reward-per-share rounding (PLTG design): extractable dust, or a griefing path?
  6. Supply identity (eq. 25): do Core.totalSupply and token.totalSupply() agree under every mint/redeem path?
  7. Collateral: can a non-standard deposit token re-enter or return false without reverting the accounting?

Appendix E — off-chain services

  • Relayer — reads up to four channels per asset, picks the primary and records confirmations, then pushes with the relayer key. Gated by a movement threshold (0.1%) with a 6-hour heartbeat ceiling so a quiet feed cannot go stale. A calm hour costs roughly 0.00003 ETH on Arbitrum Sepolia; the hourly workflow asserts that lastOracleUpdate actually moved.
  • Proof-of-reserve future — the v1 design was a daily Merkle root of custodian holdings published so anyone can verify inclusion. Requires the RWA custodian.
  • Cross-chain future — the v1 design used a bridge to widen distribution; not implemented.
  • Public read API — see Appendix B; versioned, cache-friendly, with a health endpoint for the oracle.
